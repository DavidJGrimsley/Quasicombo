For a mathematically valid braid, there is no required minimum number of choices beyond having strands and crossings. A three-strand braid can be represented by any sequence of the generators σ1, σ2, and their inverses; even a single crossing is already a nontrivial braid operation. In the three-strand braid group \(B_3\), the two basic generators are σ1 and σ2.

For Quasicombo, though, I would use at least 3 braid choices before the boss, and preferably 4.

Why 3? Because with only one choice:

σ1

you technically braided something, but you haven't really demonstrated the interesting part.

With two choices:

σ1 → σ2

you start showing that multiple exchanges can combine.

With three choices, you can get things like:

σ1 → σ2 → σ1

or:

σ2 → σ1 → σ2

which is especially relevant because the three-strand braid group has the fundamental braid relation:

σ1 σ2 σ1 = σ2 σ1 σ2

So three crossings gives you something that visibly looks and behaves like a meaningful three-strand braid rather than just one swap.

σ1

If you have time, 4 choices is better because there are more possible histories and the boss result can vary more:

σ1 → σ2⁻¹ → σ1⁻¹ → σ2

Your API already supports braid words up to many operations, so technically you aren't constrained to 3 or 4. But for a jam game, I would not make the player do 8–10 junctions just to make the quantum part “more real.”

The key is that A/B/C are the three paths/strands, while σ1 and σ2 describe crossings between those strands.

So the game should care about transitions/crossings, not the letters by themselves:

A → A = no crossing
A → B = A/B crossing = σ1 or σ1⁻¹
B → A = A/B crossing = σ1 or σ1⁻¹
B → C = B/C crossing = σ2 or σ2⁻¹
C → B = B/C crossing = σ2 or σ2⁻¹
C → C = no crossing

For the simple version, I would not allow A → C as one choice, because A and C aren't adjacent. That would need to be represented as two crossings.

No — A → C is not a problem. I’d keep your level the way you built it.

The only thing is that, for the quantum braid calculation, A → C should count as two adjacent crossings, because with three strands the elementary braid operations are only between neighboring strands.

For the simple game implementation:

A ↔ B = 1 braid operation
B ↔ C = 1 braid operation

A ↔ C = 2 braid operations

So if the player does:

A → C

you can internally treat that as:

A → B → C

and record something like:

σ1 → σ2

or the inverse-direction version depending on how that particular crossing is designed.

Likewise:

C → A

could become:

σ2⁻¹ → σ1⁻¹
What I would do in Unreal

Don't try to infer this from coordinates. Give each exit trigger a predefined braid sequence.

For example:

BP_PathChoice_AtoB
Operations:
[σ1]

BP_PathChoice_BtoC
Operations:
[σ2]

BP_PathChoice_AtoC

[σ1, σ2]

Then an A→C route can still be one continuous gameplay path. The player doesn't literally need to stop on B.

Visually:

A ───────╲
          ╲
B ────────╳────
            ╲
C ──────────╲──── PLAYER

The route passes from one side of the three-strand arrangement to the other, so internally you've crossed two neighboring strands.

One important caveat

The exact sequence depends on how you draw the crossings.

A→C isn't automatically always σ1, σ2. You also have crossing direction:

σ1
σ1⁻¹
σ2
σ2⁻¹

So when you build each route, you decide once:

“This A→C path visually goes across these two strands in this direction.”

Then assign that trigger the corresponding two-operation sequence.

For the jam, I would absolutely do it this way rather than redesign your level.
